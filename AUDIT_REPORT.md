## 1. Executive Summary

ZORQEN advertises itself as an **"Autonomous Security Validation platform for AI-built software"** combining **Static AST Analysis**, **LLM-powered threat reasoning**, and **Isolated Docker Sandbox Verification** that delivers findings that are *"confirmed, prioritized, and explained. Not just flagged."*

Following an exhaustive code-level audit, technical execution trace, and empirical test benchmarking, the definitive finding is:

> **The product does NOT function as advertised, and the backend in its current state CANNOT START UP.**

### Major Findings & Ground Truth:
1. **Critical Startup Failure (P0):** The FastAPI backend crashes immediately on boot with `pydantic.errors.PydanticUndefinedAnnotation: name 'StartAssessmentRequest' is not defined`. SlowAPI's rate limiter wrapper combined with PEP 563 (`from __future__ import annotations`) breaks Pydantic v2 type resolution in `backend/routers/api.py:1045`. As a result, the API server cannot boot, and 115 out of 125 backend tests fail to collect.
2. **The Docker Sandbox Engine Does Not Exist (P0):** Despite README claims that high-confidence findings are validated in *"isolated, disposable containers"* with *"live payload testing"* and a roadmap mark of `[x] Sandbox Verification Engine`, there is **zero container execution logic** in the backend. No Docker SDK integration, container lifecycle management, network isolation, or exploit harness exists. The frontend's `VerificationPage.tsx` even contains a hardcoded warning banner stating: *"SANDBOX VALIDATION UNAVAILABLE: Runtime exploit verification requires sandbox infrastructure."*
3. **Patch Verification is Non-Existent (P0):** Remediation patches generated by an LLM are saved as raw text diffs in the database. They are never applied to disposable working copies, never tested against security probes, and never regression-tested.
4. **False "Read-Only" GitHub Security Claim (P0):** The README explicitly claims: *"Read-only GitHub integration — OAuth-based, zero write permissions, no repository access beyond analysis."* In reality, `backend/github/oauth.py` requests `GITHUB_SCOPES = "repo read:user user:email"`. The `repo` scope is GitHub's most privileged repository scope, granting **full read/write access**. Furthermore, `backend/github/client.py` implements active mutation endpoints (`create_branch`, `create_or_update_file`, `create_pull_request`).
5. **Static AST Analysis is Actually Simple Regexes (P1):** The advertised "AST Engine" consists of 9 simple regex functions (`Stateless, regex/AST-free checks on raw source content`). Semgrep is not installed in the execution environment and falls back to these regexes. In empirical tests, the regex engine produced a false negative on standard parameterized/variable SQL queries, false positives on commented-out code, and false positives on harmless random operations.
6. **Simulated Dashboard Data & Dead Legacy Code (P1):** The frontend contains hardcoded simulated activity strings (`"Isolated sandbox container environment ready"`, `"153 codebase files indexed"`). Furthermore, the advertised **"Demo Mode"** does not exist in frontend or backend code (the `is_demo` schema columns were explicitly dropped in Alembic migration `a2b3c4d5e6f7`). Finally, six dead UI components and stylesheets from an unrelated project ("VAYU AI" city air pollution tracker) pollute the frontend.

## 4. Security Findings in ZORQEN Itself

During the engineering audit of ZORQEN's own codebase, the following vulnerabilities and security weaknesses were identified:

### [CRITICAL] 1. Misleading Privilege Escalation in GitHub OAuth Scope
- **File:** [backend/github/oauth.py:13](file:///d:/Zorqen/backend/github/oauth.py#L13)
- **Description:** ZORQEN requests `GITHUB_SCOPES = "repo read:user user:email"`. The `repo` scope gives full read and write access to code, branches, releases, and settings.
- **Impact:** Contradicts marketing and product security claims ("read-only, zero write permissions"). If ZORQEN's backend database or server is compromised, attacker acquires full read/write access to all user repositories.
- **Remediation:** If the product is truly read-only, request `public_repo` (for public repos) or convert ZORQEN to a **GitHub App** where granular read-only permissions (`contents: read`, `pull_requests: read`) can be requested.

### [HIGH] 2. In-Memory OAuth State Store Vulnerable to State Loss & Bypass
- **File:** [backend/routers/auth.py:23](file:///d:/Zorqen/backend/routers/auth.py#L23)
- **Description:** `_oauth_states: dict[str, str] = {}` stores CSRF states in a Python in-memory process dictionary.
- **Impact:** In any multi-worker setup (e.g. `uvicorn --workers 4`), Kubernetes pods, or serverless autoscaling, the OAuth callback fails with `invalid_state` if hit on a different worker. Additionally, memory leaks over time as expired states are never cleaned up.
- **Remediation:** Store OAuth states in Redis with a 10-minute TTL or sign state cryptographically in an HMAC-authenticated, short-lived cookie.

### [HIGH] 3. Token Exposure via URL Fragment & LocalStorage
- **File:** [backend/routers/auth.py:141](file:///d:/Zorqen/backend/routers/auth.py#L141), [frontend/src/services/api.ts:30](file:///d:/Zorqen/frontend/src/services/api.ts#L30)
- **Description:** The backend redirects the user to `f"{settings.frontend_url}/auth/callback#token={jwt_token}"`. The frontend reads this fragment and writes it to `localStorage.setItem('zorqen_token', fragmentToken)`.
- **Impact:** Any Cross-Site Scripting (XSS) vulnerability in the frontend application or third-party dependency can steal the JWT token from `localStorage`.
- **Remediation:** Use `HttpOnly`, `SameSite=Lax`, `Secure` cookies for session management with CSRF protection headers, rather than `localStorage`.

### [MEDIUM] 4. Commented-Out Code Triggers Critical Vulnerability Alerts
- **File:** [backend/security/custom_checks.py:100-120](file:///d:/Zorqen/backend/security/custom_checks.py#L100-L120)
- **Description:** Line-by-line regex scanning matches lines without stripping comments or verifying that the code is executable.
- **Impact:** High false-positive rates; code comments like `# cursor.execute(f"SELECT...")` generate CRITICAL security findings.
- **Remediation:** Strip comments before running regex or parse Python AST (`ast.parse`) to inspect actual Call nodes.

## 7. AI Reliability Audit

### 1. Grounding & Context Construction
- In `backend/agents/orchestrator.py:477`, findings are batched in groups of 5 (`security_reasoner.py:BATCH_SIZE = 5`).
- The LLM receives the vulnerability type, file path, line number, code snippet (truncated to 800 chars), and scanner message.
- The raw repository files are **not** sent to the LLM (mitigating data leakage and token exhaustion).
- However, the LLM is asked to output:
  - `confidence_pct` (0-100)
  - `is_exploitable` (bool)
  - `attack_path` (array of steps)
- **Hallucination Risk:** The LLM's assertion of whether something is "exploitable" is purely probabilistic speculation based on an 800-character snippet. Without runtime verification, labeling a finding "CONFIRMED" because an LLM said `is_exploitable: true` is fundamentally untrustworthy.

### 2. Model Configuration Defect
- `backend/core/config.py:271` sets `groq_model: str = "openai/gpt-oss-20b"`.
- In `test_assessment_idempotency.py:495`, the team believed `llama-3.3-70b-versatile` was "deprecated" and hardcoded `openai/gpt-oss-20b`.
- Groq does not host an OpenAI model under this identifier. When live Groq calls are attempted, it triggers `ModelNotFoundError` or HTTP 404, causing the orchestrator to fall back to un-evaluated scanner results.

### 3. Ask ZORQEN Copilot Grounding
- `backend/services/copilot.py` retrieves context directly from database models (`Finding`, `Assessment`, `Repository`).
- Prompts include system instructions enforcing a read-only role with evidence references.
- Schema validation: Validates chat requests via Pydantic (`CopilotRequest`), rate-limited to 10 requests/minute.

## 11. Prioritized Remediation Plan

### P0 — Critical Security Risks & Fundamental Correctness Failures

#### Issue 1: Backend Startup Crash on `StartAssessmentRequest`
- **Impact:** System is 100% inoperable; FastAPI fails during route declaration.
- **Evidence:** `NameError: name 'StartAssessmentRequest' is not defined` at `backend/routers/api.py:1045`.
- **Suggested Fix:** In `backend/routers/api.py`, remove `from __future__ import annotations` or define request models (`StartAssessmentRequest`, `ConnectRepoRequest`, `CopilotRequest`) in a dedicated schemas module (`schemas/assessments.py`), and ensure SlowAPI's decorator does not mask annotations from FastAPI.
- **Acceptance Criteria:** `python -c "import main"` exits 0; `pytest tests/test_auth_flow.py` collects and runs cleanly.

#### Issue 2: Misleading "Read-Only" Claim & Overprivileged OAuth Scopes
- **Impact:** Security and compliance misrepresentation; exposes customer repositories to full write compromise.
- **Evidence:** `backend/github/oauth.py:13` requests scope `repo`; `README.md:64` claims "zero write permissions".
- **Suggested Fix:** Align documentation with reality. Clearly state that `repo` scope is required for private repositories and PR generation, or transition to a GitHub App with explicit read-only granular permissions.
- **Acceptance Criteria:** README accurately reflects the exact scopes requested; no false "read-only" claims exist.

#### Issue 3: False Sandbox Engine Claims
- **Impact:** Fraudulent product marketing; customers assume findings are verified against live payloads.
- **Evidence:** README claims `[x] Sandbox Verification Engine`; zero container code exists in `backend/`.
- **Suggested Fix:** Uncheck the feature on the roadmap (`[ ] Sandbox Verification Engine`), remove payload verification claims from landing pages and README, or build an actual sandbox runner service using Docker / Firecracker.
- **Acceptance Criteria:** No marketing or UI text claims sandbox verification has occurred when only static analysis was run.

#### Issue 4: Replace Heuristic Regexes with Real AST / Semgrep Execution
- **Impact:** High false-negative rate on real code (e.g., variable SQL queries) and high false-positive rate on comments.
- **Evidence:** Empirical benchmark demonstrated 62.5% recall and failure on `query = f"..."; execute(query)`.
- **Suggested Fix:** Ensure `semgrep` binary is installed in Dockerfile and CI environments. For custom checks, use Python's built-in `ast` module (`ast.parse`) to detect variable flow and calls rather than crude regexes. Strip comments before regex matching.
- **Acceptance Criteria:** Commented lines never trigger alerts; SQL query variables are correctly identified.
